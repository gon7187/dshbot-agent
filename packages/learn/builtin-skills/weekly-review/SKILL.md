# weekly-review

Собрать обзор недели для владельца: что действительно сделано, что висит и
что стоит запланировать. Запускается из расписания в конце недели, поэтому
работает без вопросов владельцу и не выдумывает недостающие данные.

## Procedure

1. Зафиксируй окно обзора: последние семь дней по часовому поясу владельца
   (не «с понедельника» и не UTC). Запиши начало и конец окна в отчёт, чтобы
   следующий обзор не пересекался с этим.

2. Собери факты из доступных источников, ничего не пропуская молча:

   - активные и недавние задачи — `task` с `action=list` и `action=status`;
   - плановые запуски и их исходы — `schedule` с `action=history` по каждому
     заданию из `action=list`;
   - результаты в workspace: файлы и отчёты, изменённые в окне (`exec` с
     `find`/`ls -lt` по `workspace`, без выхода за его пределы);
   - память и прошлые решения — `recall` по ключевым словам недели;
   - прошлый обзор `workspace/reviews/` — что было обещано на эту неделю.

3. Раздели пункты на три группы строго по evidence:

   - **Сделано** — есть результат: файл, отчёт, закрытая задача, успешный
     плановый запуск. Ссылайся на путь, id или дату.
   - **Висит** — начато или обещано, но результата нет; укажи, чего не хватает
     и кто следующий шаг делает.
   - **Запланировать** — новые действия на следующую неделю с причиной и
     желаемым сроком. Не выдавай желаемое за уже созданное задание.

4. Проверь долги: задачи без движения больше недели, повторяющиеся ошибки
   плановых запусков, пропущенные обязательства из прошлого обзора. Отметь
   каждый отдельно, даже если он не попал в «Сделано» и не стал новой задачей.

5. Напиши отчёт в `workspace/reviews/YYYY-Www.md` (ISO-неделя) по шаблону:
   окно, «Сделано», «Висит», «Запланировать», «Требует решения владельца».
   В каждом пункте — ссылка на evidence. Держи ответ в чат коротким: 5–9
   строк и ссылка на файл; подробности остаются в файле.

6. Если обзор ставится в расписание, сначала `schedule` с `action=list`:
   задание с тем же именем не дублируй. Для еженедельного запуска используй
   `action=create`, `schedule='0 18 * * 0'` (воскресенье 18:00 по зоне
   владельца), `task` с явной ссылкой на этот навык и `idleOnly=true`.
   Плановый ход не может получить подтверждение, поэтому в задании не должно
   быть необратимых действий.

## Pitfalls

- Не считай «сделано» по факту разговора или плана: нужен артефакт, закрытая
  задача или успешный запуск. Обещание — это «висит», а не «сделано».
- Не теряй пункты, о которых нет данных: пиши «нет данных» и указывай, где
  искал, вместо молчаливого пропуска.
- Не раздувай отчёт пересказом каждого шага; владельцу нужны решения и
  застрявшее, а не протокол.
- Не создавай задачи и не меняй расписание без необходимости; если новое
  действие требует решения, вынеси его в «Требует решения владельца».
- Не путай ISO-неделю с календарной датой и не сдвигай окно на UTC.
- Если запуск планового задания упал, это факт обзора, а не повод скрыть
  остальные пункты.
- Не повторяй один и тот же пункт в двух группах: выбери главную и сошлись
  на неё из другой.

## Verification

- В отчёте явно записаны начало и конец окна, и они покрывают ровно семь дней.
- Каждый пункт «Сделано» имеет evidence: путь, id задачи или строку истории
  запуска; каждый пункт «Висит» называет недостающий результат.
- Число закрытых и висящих пунктов совпадает с числом evidence-строк; сверь
  вручную перед отправкой.
- Файл `workspace/reviews/YYYY-Www.md` существует и читается через `read`.
- В чат ушёл короткий обзор со ссылкой на файл, а не полная копия отчёта.
- `schedule action=list` показывает ровно одно еженедельное задание обзора.
