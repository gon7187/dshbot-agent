# docker-ops

Посмотреть и обслужить docker-контейнеры на серверах владельца через
`host_exec`: он ходит на ssh-алиас из `DSHBOT_HOME/hosts.json` ключом
владельца и не требует docker-сокета в песочнице. Сначала чтение, потом
одно изменение с проверкой, без массовых чисток.

## Procedure

1. Определи алиас хоста и контейнер. Алиасы перечислены в `hosts.json`; не
   придумывай имя и не ходи на хост по IP «наугад». Если владелец не назвал
   алиас и контейнер, сначала покажи список хостов и спроси.

2. Сними состояние до любых изменений:

   ```bash
   host_exec host=<alias> command="docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}'"
   host_exec host=<alias> command="docker ps -a --filter name=<name> --format '{{.ID}} {{.Status}} {{.Image}}'"
   host_exec host=<alias> command="docker inspect --format '{{json .State}}' <name>"
   ```

   Для compose-проекта добавь `docker compose -f <compose.yml> ps` и
   `docker compose -f <compose.yml> config --services`.

3. Для диагностики читай логи хвостом, а не целиком:

   ```bash
   host_exec host=<alias> command="docker logs --tail 200 --timestamps <name>"
   host_exec host=<alias> command="docker stats --no-stream <name>"
   ```

   Ищи первую ошибку, а не последнюю строку; проверь healthcheck и рестарты
   (`docker inspect --format '{{.RestartCount}} {{.State.Health.Status}}'`).

4. Изменяй по одной единице за вызов: `restart`, `stop`, `start`,
   `docker compose up -d <service>`. Перед изменением назови точный контейнер
   или сервис, ожидаемый эффект и способ отката. Команды, которые guard
   считает опасными, требуют кнопки владельца; в плановом ходе подтверждение
   недоступно, поэтому такое действие откладывается до хода владельца.

5. После изменения подожди завершения запуска и проверь результат: статус
   `running`, health `healthy` (если healthcheck есть), новые ошибки в
   `docker logs --since 2m`, доступность порта/эндпоинта. Не считай команду
   успешной только по `exit 0`.

6. Если стало хуже, верни предыдущее состояние тем же способом: `start`
   остановленного контейнера, `restart` прежнего, `compose up -d` с прежним
   тегом образа. Запиши, что именно откатили и что осталось проверить.

## Pitfalls

- Не запускай `docker system prune`, `docker volume prune`, `docker rm -f`
  и `docker compose down -v` без отдельного явного приказа: это удаляет
  данные и чужие контейнеры.
- Не путай `docker compose down` (останавливает и удаляет сеть/контейнеры
  проекта) с `stop` одного сервиса.
- Не перезапускай базу, reverse-proxy или очередь «на всякий случай»: это
  рвёт соединения зависимых сервисов.
- `docker logs` может содержать токены и персональные данные; не копируй
  весь лог в чат и не сохраняй его в публичный файл.
- Не обновляй образ тегом `latest` без фиксации прежнего image id: откат
  станет невозможен.
- `exec` в песочнице не видит docker-сокет и ключи ssh; для сервера нужен
  именно `host_exec`, а не `ssh` из `exec`.
- Не работай с чужим хостом, если алиас не совпадает с названным владельцем:
  ошибка на этом шаге необратима.

## Verification

- До и после есть вывод `docker ps`/`inspect` с одним и тем же именем
  контейнера; в ответе записан его id и образ.
- После изменения статус `running`, health не `unhealthy`, а в логах за
  последние две минуты нет новой ошибки запуска.
- Порт или health-эндпоинт отвечает так же, как до изменения (или лучше).
- Для отката снят прежний image id/тег и повторно проверено состояние.
- В ответе владельцу названы хост, контейнер, выполненные команды и итог;
  массовых `prune`/`rm` в истории нет.
