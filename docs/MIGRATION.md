# Переезд с OpenClaw

[English version](en/MIGRATION.md)

`scripts/dshbot-migrate` переносит установку OpenClaw в DSHBOT одной командой:
ключи, Telegram-бота с владельцем, MCP-серверы, навыки, память, личность и
расписания. Инструмент сначала строит
план, а пишет только по явному подтверждению. Каталог OpenClaw он не меняет
никогда: конфиг читается, SQLite открывается только на чтение (с временной
копии), файлы источника не трогаются.

Если DSHBOT только что установлен через `scripts/install.sh`, отдельная команда
обычно не нужна: установщик сам находит `~/.openclaw` (или каталог из
`OPENCLAW_STATE_DIR`) и `~/.hermes` (или `HERMES_HOME`), показывает план в
режиме `--dry-run` и предлагает применить перенос. Флаг
`--migrate=openclaw|hermes|none` задаёт источник без первого вопроса. Без
`--migrate` при `--yes` или без терминала установщик миграцию не запускает и
печатает готовую команду `dshbot-migrate` для ручного запуска, а
`--migrate=openclaw` или `--migrate=hermes` вместе с `--yes` показывает план и
применяет перенос без вопросов. Подробности — `docs/INSTALL.md`.

```sh
# посмотреть план, ничего не записывая
scripts/dshbot-migrate openclaw --dry-run

# применить (в терминале спросит подтверждение; --yes без вопроса)
scripts/dshbot-migrate openclaw --yes --include-secrets
```

`--yes` нужен и в неинтерактивном запуске (systemd, cron, скрипт): без него
печатается только план и подсказка, код выхода 0.

Конфиг `openclaw.json` (и старые `clawdbot.json`, `moltbot.json`) читается как
JSON5: комментарии, висячие запятые, ключи без кавычек, строки в одинарных
кавычках и числа вида `0x7b`, `+123`, `.5`, `5.`, `Infinity`, `NaN`.

## Флаги

| Флаг | Значение |
| --- | --- |
| `--from <каталог>` | каталог состояния OpenClaw; без него — автопоиск: `$OPENCLAW_STATE_DIR`, затем `~/.openclaw`, `~/.clawdbot`, `~/.moltbot` с файлом `openclaw.json`, `clawdbot.json` или `moltbot.json` |
| `--home <каталог>` | `DSHBOT_HOME`; по умолчанию `$DSHBOT_HOME` или `~/.local/share/dshbot` |
| `--env-file <путь>` | файл окружения демона (его читает systemd через `EnvironmentFile`); по умолчанию `~/.config/dshbot/dshbot.env` |
| `--dry-run` | только план: ни один файл не создаётся и не меняется |
| `--yes` | применить без вопроса; в терминале без флага задаётся вопрос «да/нет» |
| `--include-secrets` | переносить значения секретов; без него только имена в плане и отчёте |
| `--overwrite` | заменять уже существующие значения (по умолчанию они не меняются, а получают статус `конфликт`) |
| `--skill-conflict <режим>` | что делать, если навык с таким именем уже есть в `DSHBOT_HOME/skills`: `skip` (по умолчанию, статус `конфликт`), `rename` (копия как `<name>-openclaw`, следующая — `<name>-openclaw-2`) или `overwrite` (заменить обычный навык; встроенный не заменяется никогда) |
| `--json` | машинный вывод одним JSON-документом |

Каждый элемент плана печатается одной строкой: вид, имя, цель и статус
(`план`, `применено`, `пропущено`, `конфликт`, `ошибка`, `предупреждение`).
Значения секретов не печатаются нигде — ни в stdout, ни в отчёте, ни в журнале.

С `--json` в stdout всегда ровно один JSON-документ: поле `applied` говорит,
было ли применение, `items` — элементы плана, `report` — путь к отчёту после
применения. Без `--yes` в неинтерактивном запуске подсказка про `--yes` лежит в
поле `hint`, а не отдельной строкой. В терминале без `--yes` план и вопрос
«да/нет» уходят в stderr, чтобы stdout остался одним документом.

## Что переносится

### Ключи и секреты

Источники:

- переменные `<state>/.env` (строки `KEY=value`, в том числе `export KEY=value`);
- `env.vars.<NAME>` из `openclaw.json`;
- `models.providers.<p>.apiKey` — строкой или `SecretRef` с `source: env`;
- секретные поля `plugins.entries.<p>.config.*` (имена с `token`, `key`,
  `secret`, `password`, `authorization`);
- живые записи `secret_store_entries` из `<state>/state/openclaw.sqlite`
  (`deleted_at_ms IS NULL`);
- профили `api_key` из `agents/<id>/agent/auth-profiles.json` и из таблицы
  `auth_profile_store` в `agents/<id>/agent/openclaw-agent.sqlite`;
- файлы `<state>/credentials/` (кроме `telegram-*allowFrom*.json`): значение —
  содержимое файла целиком, байт в байт (двоичные файлы тоже).

Значения конфига OpenClaw с подстановкой `${NAME}` разворачиваются так же, как
это делает OpenClaw: сначала из `<state>/.env`, затем из `env.vars.*` (с учётом
ссылок переменных друг на друга), затем из окружения процесса. Подстановка
работает и внутри строки, например `Authorization: "Bearer ${HA_TOKEN}"`;
`$${NAME}` остаётся буквальным `${NAME}`. Пустое значение считается
отсутствующим. Если переменной нет нигде, в плане появляется `предупреждение` с
именем переменной и путём поля — без значения, а значение с неразрешённой
подстановкой в хранилище не записывается.

Куда:

- `TELEGRAM_BOT_TOKEN`, `DEEPSEEK_API_KEY`, `DEEPSEEK_BASE_URL` дописываются в
  файл окружения демона, из какого бы источника они ни пришли: `.env`,
  `env.vars`, `models.providers.deepseek.apiKey`, `secret_store_entries` или
  профиль авторизации провайдера `deepseek`. Существующие строки не меняются;
  файл получает режим `0600`. Если файла нет, он создаётся только когда есть
  что дописать.
- Файл окружения читается по правилам systemd `EnvironmentFile=` (кавычки,
  экранирование `\"`, `\\`, `\$`, `` \` ``, перенос строки внутри кавычек), так
  что ключ, уже записанный владельцем в другом виде кавычек с тем же значением,
  считается перенесённым. Значения с пробелами и спецсимволами записываются в
  двойных кавычках с тем же экранированием: их одинаково читают systemd и
  POSIX shell.
- Все остальные ключи — в хранилище `DSHBOT_HOME/secrets/<NAME>` с режимом
  `0600` (тот же формат, что у демона: `^[A-Z0-9_]{1,64}$`, значение — файл).
- Одинаковое имя с одинаковым значением — одна запись. Одинаковое имя с разными
  значениями — `конфликт`.

Имена:

- переменные из `.env`, `env.vars.*` и `secret_store_entries` сохраняют свои имена;
- ключ провайдера получает имя `<PROVIDER>_API_KEY` (например, `zhipu` →
  `ZHIPU_API_KEY`), в том числе для профилей авторизации;
- поля плагинов и прочие поля конфига получают имя, детерминированно выведенное
  из пути поля (`plugins.entries.sample.config.token` →
  `PLUGINS_ENTRIES_SAMPLE_CONFIG_TOKEN`); в отчёте видна пара «путь → имя».
- `SecretRef` с `source: env` разрешается как подстановка `${NAME}`: по
  `<state>/.env`, `env.vars.*` и окружению процесса. `source: file` и `source: exec` автоматически не разрешаются:
  элемент получает `предупреждение` с путём поля. OAuth-профили не переносятся,
  об этом тоже есть строка в отчёте.

Без `--include-secrets` ни один файл в `DSHBOT_HOME/secrets` не создаётся и
файл окружения не меняется; в выводе перечислены имена ключей, которые были бы
перенесены, и подсказка повторить с `--include-secrets`. Владелец и
MCP-серверы при этом переносятся (ссылки на секреты в `mcp.json` остаются, но
значений в хранилище нет, пока их не перенести с `--include-secrets`).

### Telegram: токен и владелец

Токен берётся из `channels.telegram.botToken` или
`channels.telegram.accounts.<defaultAccount>.botToken` (активный аккаунт —
`defaultAccount`, иначе единственный аккаунт). Поддерживаются строка,
вид `${ENV}` и `SecretRef` с `source: env`.

Владелец пишется в `state.db` под ключом `telegram.owner_chat_id`, чтобы первое
сообщение владельца не требовало кода привязки. Источник выбирается по порядку:

1. первый Telegram id из `commands.ownerAllowFrom` (`telegram:123` и `123` дают `123`);
2. `allowFrom` активного аккаунта;
3. `channels.telegram.allowFrom`;
4. `channel_pairing_allow_entries` в SQLite источника;
5. `credentials/telegram-*allowFrom*.json`.

Если в `state.db` уже записан другой владелец, значение не меняется, элемент
получает `конфликт`; `--overwrite` заменяет его.

### MCP-серверы

`mcp.servers.<name>` переносится в `DSHBOT_HOME/mcp.json` как
`mcpServers.<name>` с полями `command`, `args`, `cwd`, `url`, `transport`,
`enabled` (и `requestTimeoutMs`, если он был). Другие серверы в `mcp.json`
сохраняются.

Значения `env` и `headers` с секретными именами (`token`, `key`, `secret`,
`password`, `authorization` без учёта регистра) заменяются ссылкой
`${secret:NAME}`, а значение уходит в хранилище при `--include-secrets`. Так
же переносится значение `env` и `headers` с любым именем, в котором сработала
подстановка `${NAME}`: развёрнутый текст попадает только в хранилище, а не в
`mcp.json`. Если подстановка не разрешилась, ссылка остаётся без значения в
хранилище, и DSHBOT покажет для сервера ненайденный секрет.
Сервер с тем же именем не меняется и получает `конфликт`; `--overwrite`
заменяет его. Команда, которой нет в `PATH` и нет по абсолютному пути, даёт
`предупреждение`, но сервер всё равно переносится. Если `command` или `cwd`
нельзя выполнить или открыть, абсолютный путь из `args` или `env` (кроме
секретных полей) нельзя прочитать, или любой из них лежит в каталоге,
недоступном текущему пользователю, сервер тоже переносится, но план содержит
`предупреждение` с именем сервера и самим путём: иначе такой сервер молча не
запустится после миграции.

### Навыки

Рабочая папка главного агента — `agents.entries.main.workspace`, иначе
`agents.defaults.workspace`, иначе `<state>/workspace`. Навыки читаются по
приоритету: `<workspace>/skills`, `<workspace>/.agents/skills`, `~/.agents/skills`
(родитель каталога состояния), `<state>/skills`,
`<state>/agents/main/agent/workshop-skills`. При совпадении имени побеждает
каталог с большим приоритетом; каталоги с именем на точку (резервные копии
`.name-before-…`) не копируются.

Каждый навык целиком копируется в `DSHBOT_HOME/skills/<name>/` со всеми файлами
(`scripts/`, `references/`, `routes.json`, двоичными вложениями) и получает
`.meta.json` с `imported: true` — тот же признак, по которому `packages/learn`
показывает импортированные навыки. Навык с `metadata.openclaw.os`, где нет
`linux`, пропускается с причиной про платформу.

`skills.entries.<ключ>.env.*` и `skills.entries.<ключ>.apiKey` уходят в
хранилище секретов с `--include-secrets`; `apiKey` получает имя из
`metadata.openclaw.primaryEnv` навыка. Без флага имена видны в плане и отчёте,
значения не пишутся. Если значение любого секрета источника встречается в
скопированном файле, навыке или тексте памяти, оно заменяется на `[скрыто]`, а
отчёт предупреждает об этом с именем файла. Ключ лучше передавать через
`secrets` инструмента `exec`, а не хранить текстом навыка.

### Память и личность

`MEMORY.md` и `USER.md` рабочей папки дописываются в
`DSHBOT_HOME/memory/MEMORY.md` и `DSHBOT_HOME/memory/USER.md`: абзацы, которые
уже есть, не повторяются. Дневные заметки `memory/YYYY-MM-DD.md` идут в
`DSHBOT_HOME/memory/journal/YYYY-MM-DD.md`; существующий файл получает дописку
под заголовком «Из OpenClaw».

`SOUL.md` и `IDENTITY.md` — личность. Если `memory/identity.md` нет или он
совпадает с затравкой `persona/identity.seed.md`, текст пишется туда; при своей
личности он не меняется, а текст сохраняется в
`memory/knowledge/openclaw-persona.md` со статусом `конфликт`. `--overwrite`
заменяет `identity.md`, прежний текст кладётся в `before/`. `AGENTS.md`,
`TOOLS.md`, `HEARTBEAT.md`, `BOOTSTRAP.md` переносятся в
`memory/knowledge/openclaw-<имя строчными>.md`. Рабочие папки других агентов не
переносятся.

При повторном запуске каждый файл знаний сравнивается с тем, что записала
последняя миграция (её отпечатки хранятся в `migration/openclaw-state.json`). Если
владелец не менял файл, изменившийся текст источника обновляет его без
конфликта. Если файл в DSHBOT отличается и от нового текста источника, и от
записи прошлой миграции, это правка владельца: элемент получает `конфликт`, а
файл не меняется. `--overwrite` заменяет его текстом источника, а прежние
байты владельца кладутся в `before/` отчёта.

### Расписания

Задачи читаются из `<state>/state/openclaw.sqlite` (таблица `cron_jobs`) или из
старого `<state>/cron/jobs.json` и создаются в расписаниях DSHBOT
(`state.db`, `packages/scheduler`):

- `cron` → пятиполевое выражение с зоной `schedule.tz`;
- `every` → `every <N>m|h|d`; интервал, не кратный минуте, округляется вверх с
  предупреждением;
- `at` в будущем → разовый запуск; `at` в прошлом пропускается с причиной;
- текст задания — `payload.message` или `payload.text`;
- `enabled: false` → расписание создаётся на паузе;
- служебные задания OpenClaw, весь текст которых имеет вид
  `__openclaw_…__` (`__openclaw_memory_core_short_term_promotion_dream__` и
  подобные), пропускаются с причиной: они не предназначены для модели и не
  должны выполняться как обычное расписание;
- абсолютные пути перенесённых навыков в тексте задания заменяются на
  `DSHBOT_HOME/skills/<name>/SKILL.md`, в том числе при переименовании навыка
  из-за коллизии (`<name>-openclaw`), и через реальный путь, если `--from` —
  символическая ссылка; путь к каталогу навыка заменяется на
  `DSHBOT_HOME/skills/<name>`. Пути других навыков с тем же началом имени не
  меняются.

Задачи с `payload.kind` `command`, `script`, `heartbeat` и задачи не главного
агента не создаются: они перечисляются с именем, расписанием и командой или
текстом в `<каталог отчёта>/manual-review.md`, решение принимает владелец.
Повторный запуск не плодит дублей.

Перенесённое расписание сопоставляется с задачей источника по её устойчивому
идентификатору (`job_id` в SQLite или `id`, а без него — имя из
`cron/jobs.json`), а не по паре «расписание и текст». Идентификаторы
расписаний DSHBOT сохраняются в `$DSHBOT_HOME/migration/openclaw-state.json`
при первом переносе. Если при том же идентификаторе в OpenClaw изменился текст
задания или расписание, элемент получает `конфликт` с причиной, а
существующая строка остаётся прежней; второго расписания не появляется.
`--overwrite` обновляет текст и расписание той же строки, сохраняя её `id`.
Задача источника с другим идентификатором, но с тем же текстом и расписанием,
что у уже перенесённой задачи, второй строки не создаёт: она отмечается в
отчёте как `skipped` с причиной «уже есть», а её идентификатор в карту не
записывается. Когда такая задача изменится в OpenClaw, она переносится
отдельным расписанием, а строка другой задачи не меняется. Задача со своей
строкой при изменении получает конфликт или, с `--overwrite`, обновление
только своей строки.
Строка, созданная прошлой версией миграции без сохранённого идентификатора, но
с тем же текстом и расписанием, принимается как уже перенесённая: дубль не
создаётся, а её идентификатор записывается в карту для следующих запусков.
Прошлая версия объединяла одинаковые задачи в одну строку; строка достаётся
первой из них, а остальные пропускаются так же, как описано выше.
Повторный запуск без изменений не меняет ни строк `schedules`, ни файлов в
`DSHBOT_HOME` и завершается кодом `0`.

## Отчёт и копии

После применения создаётся
`$DSHBOT_HOME/migration/openclaw-<время>/report.json` с режимом `0600`. В нём
перечислены элементы (вид, имя, источник, цель, статус, путь поля для
выведенных имён, причина) — без значений секретов. Перед изменением
существующих файлов (файла окружения, `mcp.json`, навыка при
`--skill-conflict overwrite` или `--overwrite`, `identity.md`, файла знаний при
`--overwrite`) их точные копии кладутся в `<каталог отчёта>/before/` с режимом
`0600`. Навык сохраняется целиком, со всеми файлами и `.meta.json`. Если есть
задачи для ручного разбора, рядом появляется `manual-review.md`. Рядом с
каталогами отчётов в `migration/openclaw-state.json` хранится карта
«идентификатор задачи OpenClaw → строка `schedules`» и отпечатки записанных
файлов знаний; она обновляется только при изменении, поэтому повторный запуск
без правок не создаёт новых файлов.

Если каталог отчёта создать нельзя, миграция ничего не применяет (без него нет и
копий в `before/`); если не записался сам `report.json`, применённое остаётся, а
запуск считается неудачным. Сообщение об этом и о любой неожиданной ошибке
уходит в stderr одной строкой без стека; известные значения секретов в нём, как
и в путях, заменены на `${secret:ИМЯ}`. С `--json` сообщение о сбое отчёта
лежит и в поле `error` документа.

Код выхода `1`, если есть `конфликт` или `ошибка`; иначе `0`. Повторный запуск с
тем же источником ничего не меняет: элементы помечаются как уже перенесённые, а
новый отчёт не создаётся.

## Переезд с Hermes

Второй источник того же инструмента:

```sh
# план по элементам, ничего не записывая
scripts/dshbot-migrate hermes --dry-run

# применить (в терминале спросит подтверждение; --yes без вопроса)
scripts/dshbot-migrate hermes --yes --include-secrets

# именованный профиль ~/.hermes/profiles/work
scripts/dshbot-migrate hermes --profile work --dry-run

# конкретный каталог установки
scripts/dshbot-migrate hermes --from /srv/hermes --yes --include-secrets
```

Каталог выбирается так: `--from`, иначе `$HERMES_HOME`, иначе `~/.hermes`.
`--profile <имя>` добавляет `profiles/<имя>` к этому корню. Флаги `--home`,
`--env-file`, `--dry-run`, `--yes`, `--include-secrets`, `--overwrite` и
`--json` работают так же, как у OpenClaw; отчёт лежит в
`$DSHBOT_HOME/migration/hermes-<время>/report.json`.

### Ключи и секреты

- `.env` читается как `KEY=value`. Секретами считаются имена с `KEY`, `TOKEN`,
  `SECRET` или `PASSWORD` без учёта регистра, а также `*_BASE_URL`, если рядом
  есть `<ПРЕФИКС>_API_KEY`. Имя в хранилище — имя переменной в верхнем регистре.
- `TELEGRAM_BOT_TOKEN`, `DEEPSEEK_API_KEY` и `DEEPSEEK_BASE_URL` идут в файл
  окружения демона, а не в `secrets/`.
- Остальные переменные — настройки Hermes (`TERMINAL_TIMEOUT`,
  `WEB_TOOLS_DEBUG` и подобные): они не переносятся и перечисляются в отчёте.
- `auth.json`: записи `credential_pool.<провайдер>` с `auth_type: api_key` и
  `source: env:NAME` разрешаются по `.env` и не создают второго ключа.
  OAuth-записи (`access_token`, `refresh_token`) не переносятся, о каждой есть
  строка в отчёте.
- Файлы `credentials/` переносятся целиком, байт в байт (двоичные тоже), в
  `secrets/`; имя выводится из имени файла (например, `service-account.json` →
  `CREDENTIALS_SERVICE_ACCOUNT_JSON`).

### Telegram

Токен берётся из `TELEGRAM_BOT_TOKEN` в `.env`. Владелец выбирается по порядку:
первый id из `TELEGRAM_ALLOWED_USERS` (список через запятую), иначе первый id из
`telegram-pairing/telegram-approved.json`, иначе `TELEGRAM_HOME_CHANNEL`. Если в
живом процессе запущен Hermes gateway — `hermes-gateway`, `hermes gateway`,
путь вида `.../hermes/.../gateway` или `python -m hermes_cli[.main] gateway`, —
токен не переносится: Telegram отвечает `409 Conflict`, когда один токен
одновременно используют два бота. Элемент получает `конфликт` с объяснением,
остальное применяется. Решает сама запускаемая программа: исполняемый файл,
скрипт интерпретатора (`python3 ~/.local/bin/hermes gateway`) или модуль после
`-m`, стоящего среди опций Python до скрипта. Посторонний скрипт с этими словами
в аргументах (`python /srv/report.py -m hermes_cli.main gateway`,
`node /srv/report.js hermes gateway`) gateway не считается.

### MCP-серверы

`config.yaml` (YAML) читается без переноса остальных разделов.
`mcp_servers.<имя>` → `mcp.json`, `mcpServers.<имя>`: `command`, `args`, `cwd`,
`url`, `enabled`, а `tools.include`/`tools.exclude` — в одноимённые поля
политики инструментов. Значения `env` и `headers` с секретными именами
(`token`, `key`, `secret`, `password`, `authorization`) заменяются ссылкой
`${secret:NAME}`, значение уходит в хранилище при `--include-secrets`.
Разделы `model`, `agent`, `terminal`, `browser` и прочие не переносятся
(DSHBOT работает на DeepSeek) и перечисляются в отчёте.

### Навыки

Поддерживаются обе раскладки: `skills/<категория>/<имя>/SKILL.md` и
`skills/<имя>/SKILL.md`. Навык копируется целиком в `<home>/skills/<имя>/` со
всеми файлами и помечается импортированным (`.meta.json`). Если одно имя
встречается в разных категориях, каталоги получают имена
`<категория>-<имя>`, а `name` во frontmatter SKILL.md переписывается под новое
имя при любой записи ключа в YAML (`name:`, `"name":`, `'name':`, многострочное
значение). Навыки из `skills.disabled` и навыки с `platforms` без `linux` не
копируются, причина видна в отчёте. Существующий навык с другим содержимым даёт
`конфликт`; `--skill-conflict overwrite` (или `--overwrite`) заменяет его, а
прежнее дерево навыка целиком, включая скрытые файлы, вложенные каталоги и
`.meta.json`, сохраняется в `before/` отчёта — так же, как при замене навыка из
OpenClaw.

Значения ключей этого переноса (хранилище и файл окружения, от 8 символов),
найденные в текстовых файлах навыка, заменяются ссылкой `${secret:NAME}`, как в
`mcp.json`. Двоичные файлы копируются байт в байт.

### Память и личность

`memories/MEMORY.md` и `memories/USER.md` делятся на записи строкой `§` и
дописываются в `memory/MEMORY.md` и `memory/USER.md` без повторов уже
имеющихся записей. `MEMORY.md.lock` и `MEMORY.md.bak*` не читаются. `SOUL.md`
становится `memory/identity.md` по тому же правилу, что и у OpenClaw: пустая
личность заполняется, совпадающая пропускается, другая без `--overwrite` даёт
`конфликт`, а замена с `--overwrite` проходит порог длины identity.

### Расписания

`cron/jobs.json` (`{jobs: [{id, name, prompt, schedule, repeat, enabled,
state}]}`) переносится в `state.db` DSHBOT:

- `{kind: cron, expr}` → то же cron-выражение;
- `{kind: interval, minutes}` → `every <N>m`;
- `{kind: once, run_at}` в будущем → разовый запуск; в прошлом — пропуск с
  причиной;
- `prompt` становится текстом задания символ в символ (с пробелами и переводами
  строк по краям), а `repeat.times` — ограничением числа запусков (`maxRuns`);
- `enabled: false` или `state: paused` → расписание создаётся на паузе.

При повторном запуске каждое расписание DSHBOT сопоставляется не больше чем с
одной задачей: сначала по тексту задания вместе с расписанием, ограничением и
паузой (такие пропускаются как уже перенесённые), затем по одному тексту
(`конфликт`, а с `--overwrite` — обновление). Поэтому несколько задач с одним
`prompt` и разными расписаниями повторно ничего не меняют.

Задачи со `script` или `no_agent` не переносятся автоматически: они попадают в
`$DSHBOT_HOME/migration/manual-review.md` с текстом задания и скриптом для
ручной проверки; значения ключей этого переноса в них заменены ссылкой
`${secret:NAME}`. `sessions`, `state.db`, `kanban`, `webhook` и остальные
служебные данные Hermes не переносятся и перечисляются в отчёте.

## Ограничения

- Пока `dshbot-migrate` не переносит OAuth-профили, `SecretRef` с `source:
  file`/`exec` и сами файлы `telegram-*allowFrom*.json` (это идентификаторы, а
  не секреты).
- Применение отказывает, если с этим `DSHBOT_HOME` уже работает демон DSHBOT:
  ничего не записывается, код выхода `1`. `--dry-run` при этом работает.
  Остановите демон и повторите.

## Один токен на двух ботах

Telegram отдаёт `409 Conflict`, если один и тот же токен одновременно
используют два процесса `getUpdates`: OpenClaw gateway, Hermes gateway и DSHBOT.
Поэтому при живом gateway источника токен не переносится, элемент получает
`конфликт`, а остальное переносится. Для OpenClaw живым считается процесс, в
аргументах которого есть `openclaw` (или путь к нему) и отдельный `gateway` без
учёта регистра: `openclaw gateway`, `openclaw-gateway`, путь вида
`/opt/openclaw/.../gateway`. Для Hermes решает запускаемая программа или скрипт
интерпретатора: `hermes-gateway`, `hermes gateway`, путь вида
`.../hermes/.../gateway` или `python -m hermes_cli[.main] gateway`; слова
`hermes gateway` в аргументах постороннего скрипта не в счёт. Сам
`dshbot-migrate` к ним не относится. Остановите источник — или заведите нового
бота в [@BotFather](https://t.me/BotFather) и положите его токен в DSHBOT.
