# Установка DSHBOT

[English version](en/INSTALL.md)

Установщик — `scripts/install.sh` в корне репозитория. Одна команда ставит приложение, зависимости, настройки и пользовательские службы systemd, запускает бота и помогает выполнить привязку владельца.

## Что нужно

- Linux с пользовательским systemd (`systemctl --user`).
- Node.js не ниже версии из `engines` в `package.json`.
- `git`.
- `bwrap` (bubblewrap) — обязательно для режима `container`, необязательно для `host`.

Установщик проверяет всё это до любых изменений: при ошибке он печатает понятное сообщение по-русски, завершается с ненулевым кодом и ничего не создаёт.

## Гостевой exec и Node вне HOME

Гостевой `exec` запускает прокси песочницы и саму команду на Node вне `HOME` пользователя: песочница гостя маскирует домашний каталог, поэтому установки mise и nvm под `HOME` гостю не видны. Установщик проверяет это и, если единственный Node лежит под `HOME`, завершает установку как обычно, но печатает предупреждение с подсказкой. Поставьте системный Node пакетным менеджером, например `sudo apt install nodejs` или `sudo dnf install nodejs`, либо укажите путь к Node вне `HOME` так, чтобы `node` находился через `PATH` демона. Без такого Node каждый `exec` гостя отклоняется понятной ошибкой «нет Node вне каталогов владельца», а остальной ход гостя остаётся доступен.

## Быстрый старт

Интерактивный режим:

```sh
scripts/install.sh
```

Установщик спросит:

1. токен бота Telegram (`TELEGRAM_BOT_TOKEN`);
2. ключ DeepSeek (`DEEPSEEK_API_KEY`);
3. режим изоляции `container` или `host` (`DSHBOT_ISOLATION`).

Введённые токен и ключ не печатаются. Если переменная уже задана в окружении, соответствующий вопрос пропускается.

Неинтерактивный режим:

```sh
TELEGRAM_BOT_TOKEN=... \
DEEPSEEK_API_KEY=... \
DSHBOT_ISOLATION=container \
scripts/install.sh --yes
```

С `--yes` вопросов нет: недостающие значения берутся только из окружения, а при их отсутствии установка завершается ошибкой. Флаг можно писать как `--yes` или `-y`.

## Переезд с OpenClaw или Hermes

После успешной установки `scripts/install.sh` проверяет, есть ли уже данные другого агента:

- OpenClaw — каталог из `$OPENCLAW_STATE_DIR`, иначе `~/.openclaw`;
- Hermes — каталог из `$HERMES_HOME`, иначе `~/.hermes`.

Файл с таким именем источником не считается: нужен именно каталог. Если не найдено ни одного каталога, установщик ничего не спрашивает и не упоминает миграцию.

Когда источник найден, установщик печатает его имя и путь. В терминале он спрашивает, перенести данные сейчас; если найдены оба каталога, предлагает выбрать `openclaw`, `hermes` или отказ. При согласии сначала запускается `dshbot-migrate --dry-run`: установщик показывает план и отдельно спрашивает подтверждение применения. Только после второго «да» миграция применяется (`--yes` у `dshbot-migrate`). Применение идёт при остановленной службе `dshbot.service`, после чего установщик снова её запускает. Если остановить службу не удалось, миграция не применяется: установщик предупреждает об этом и печатает готовую команду, служба продолжает работать.

Без `--migrate` при флаге `--yes` или без терминала установщик не задаёт вопросов и не запускает миграцию: он печатает готовую команду `dshbot-migrate` с источником и найденным путём. Скопируйте её, если хотите перенести данные позже: в терминале она покажет план и спросит подтверждение. Перед запуском остановите службу (`systemctl --user stop dshbot.service`), а после переноса запустите её снова; установщик делает так же для автоматического применения. Команда использует полный путь к установленной копии `dshbot-migrate` и закреплённый `node` из юнитов, поэтому работает даже когда `node` нет в `PATH`.

Источник можно выбрать без вопроса флагом `--migrate=openclaw|hermes|none`:

| Значение | Поведение |
| --- | --- |
| `--migrate=openclaw` | сразу пробный прогон OpenClaw, без первого вопроса |
| `--migrate=hermes` | сразу пробный прогон Hermes, без первого вопроса |
| `--migrate=none` | не предлагать миграцию и не запускать её |

Без `--yes` после пробного прогона всё равно задаётся вопрос о применении; без терминала этот вопрос не задаётся и считается отказом: установщик показывает план и печатает готовую команду. С `--yes` миграция применяется без вопросов. Если каталог выбранного источника не найден, установщик предупреждает, не вызывает `dshbot-migrate`, но установка завершается успешно. Неизвестное значение (например `--migrate=foo`) отклоняется с сообщением о допустимых значениях до любых изменений.

Ошибка миграции не отменяет установку: установщик сообщает, что миграция не удалась, и печатает её код возврата, но бот остаётся установленным и служба запущена. Установщик запускает миграцию с `--include-secrets`, чтобы перенести значения ключей, но в выводе `install.sh` секретов нет — ни введённых при установке, ни прочитанных из `dshbot.env`: план и отчёт показывают только имена.

Подробнее о самом переносе — `docs/MIGRATION.md`.

## Куда что ставится

| Что | Путь |
| --- | --- |
| Приложение (git-клон, ветвь `live`) | `~/.local/share/dshbot/app` (или `$DSHBOT_HOME/app`) |
| Данные бота, память, `state.db` | `~/.local/share/dshbot` (или `$DSHBOT_HOME`) |
| Настройки | `~/.config/dshbot/dshbot.env` (права `600`) |
| Службы | `~/.config/systemd/user/dshbot.service`, `~/.config/systemd/user/dshbot-doctor.service` |

Настройки и службы всегда лежат в `~/.config`, `XDG_CONFIG_HOME` не учитывается: доктор читает именно `~/.config/dshbot/dshbot.env`, а файловые инструменты бота скрывают именно `~/.config/dshbot`. Файл с ключами в другом месте стал бы доступен боту.

Юниты установщик собирает из `deploy/*.service` каталога приложения и пишет обычными файлами. Путь к `node` он находит сам (`process.execPath`) и подставляет вместо шима `mise`. В основном юните `ExecStart` начинается с этого пути `node` и запускает мост `<DSHBOT_HOME>/dshbot-launch.mjs`, который передаёт управление `app/scripts/dshbot-run.sh`: выбор `host`/`container` остаётся за лаунчером. Если задан собственный `DSHBOT_HOME`, он подставляется вместо `%h/.local/share/dshbot` в `WorkingDirectory`, `Environment=DSHBOT_HOME`, `NODE_COMPILE_CACHE`, `ExecStartPre` и `ExecStart`. Файлы юнитов в репозитории остаются рабочими шаблонами с `%h/.local/share/mise/shims/node`: существующие установки, которые подключали `deploy/*.service` симлинком, продолжают работать.

## Origin и самообновление

`/update` и отправка принятых правок в main работают через `remote origin` приложения. При новой установке установщик берёт `remote.origin.url` источника — checkout из `DSHBOT_INSTALL_SRC` или корня репозитория — и добавляет этот адрес приложению. Локальный путь к источнику в origin не попадает: там оказывается, например, адрес GitHub. Относительный путь origin источника (`../remote.git`) разрешается в абсолютный путь от каталога источника, а учётные данные (`https://user:token@host/repo.git`) из адреса удаляются, чтобы токен не попал в `.git/config` приложения и в вывод установщика. Учётными данными считается только часть перед `@` в имени хоста: `@` в пути (`file:///srv/upstream@mirror.git`) и адреса вида `git@github.com:owner/dshbot.git` остаются как есть, а у `ssh://git@host/repo.git` сохраняется имя пользователя ssh — удаляется только пароль.

Адрес можно задать явно переменной `DSHBOT_INSTALL_ORIGIN`; она важнее origin источника:

```sh
DSHBOT_INSTALL_ORIGIN=git@github.com:owner/dshbot.git scripts/install.sh --yes
```

При обновлении установки, созданной установщиком, отсутствующий origin добавляется по тем же правилам. Уже существующий origin приложения не меняется, даже если задана `DSHBOT_INSTALL_ORIGIN`. Связанный worktree другого репозитория установщик не трогает: его remote-конфиг общий с этим репозиторием.

### Авторизация GitHub для /update и отправки правок

Если origin приложения — `https://github.com/...`, установщик проверяет `gh` в `PATH` и его авторизацию (`gh auth status`). Когда `gh` авторизован, в локальный конфиг репозитория приложения записывается credential helper:

```sh
credential.https://github.com.helper = "!<абсолютный путь к gh> auth git-credential"
```

Путь — тот, по которому `gh` найден в `PATH`, приведённый к абсолютному; символическая ссылка не раскрывается. Например, для `/snap/bin/gh` в helper попадает `/snap/bin/gh`, а не цель ссылки `/usr/bin/snap`: такой диспетчер выбирает программу по имени, под которым его запустили. git запускает такой helper через `sh -c`, поэтому путь с пробелом или другим особым для shell символом записывается в одинарных кавычках, например `!'/opt/GitHub CLI/gh' auth git-credential`, а одинарная кавычка внутри пути — как `'\''`: для `/opt/owner's-tools/gh` в helper попадает `!'/opt/owner'\''s-tools/gh' auth git-credential`. Так записывается любой абсолютный путь к авторизованному `gh`.

Это нужно потому, что эволюция и синхронизация запускают git с `GIT_CONFIG_GLOBAL=/dev/null`; глобальный helper, который создаёт `gh auth setup-git`, им не виден. Повторная установка не добавляет второй helper с тем же значением. Связанный worktree (`.git` — файл) установщик не меняет: его конфиг общий с чужим репозиторием.

Если `gh` нет в `PATH` или он не авторизован, установка завершается успешно, helper не записывается, а установщик печатает подсказку. Выполните:

```sh
gh auth login
scripts/install.sh --yes
```

Второй запуск запишет helper, после чего `/update` и отправка правок в main смогут работать без доступа к глобальному git-конфигу. Проверить запись можно командой:

```sh
git -C ~/.local/share/dshbot/app config --local --get-all credential.https://github.com.helper
```

Если у источника нет origin и `DSHBOT_INSTALL_ORIGIN` не задана, origin не создаётся. Установка завершается успешно, но установщик предупреждает, что самообновление (`/update` и отправка правок в main) будет недоступно, и печатает готовую команду:

```sh
git -C ~/.local/share/dshbot/app remote add origin <адрес>
```

## Переменные env-файла

`~/.config/dshbot/dshbot.env` читается службами через `EnvironmentFile`. Установщик создаёт файл один раз и никогда не перезаписывает существующий.

| Переменная | Назначение |
| --- | --- |
| `TELEGRAM_BOT_TOKEN` | токен бота от [@BotFather](https://t.me/BotFather) |
| `DEEPSEEK_API_KEY` | ключ API DeepSeek |
| `DSHBOT_ISOLATION` | режим запуска: `container` или `host` |
| `DSHBOT_OPENAI_PORT` | порт OpenAI-совместимого эндпоинта для голосовых клиентов (вместе с токеном) |
| `DSHBOT_OPENAI_TOKEN` | bearer-токен OpenAI-совместимого эндпоинта; без него эндпоинт не запускается |
| `DSHBOT_OPENAI_HOST` | адрес прослушивания OpenAI-совместимого эндпоинта, по умолчанию `127.0.0.1` |
| `DSHBOT_OPENAI_TLS_CERT` | путь к PEM-сертификату для HTTPS эндпоинта |
| `DSHBOT_OPENAI_TLS_KEY` | путь к PEM-ключу сертификата |
| `DSHBOT_NOTIFY_QUEUE` | каталог очереди карточек сборщиков; по умолчанию `$DSHBOT_HOME/notification-queue` |

Дополнительные параметры можно дописать в файл руками: при обновлении установщик сохраняет файл как есть.

### OpenAI-совместимый API

Эндпоинт `POST /v1/chat/completions` — общий OpenAI-совместимый API для голосовых и
других клиентов. Xiaozhi — один из примеров такого клиента: xiaozhi-server на том же
сервере может отдавать задачи голосовой модели в DSHBOT вместо шлюза OpenClaw.
Эндпоинт повторяет OpenAI-совместимый вызов: заголовок
`Authorization: Bearer <DSHBOT_OPENAI_TOKEN>`, тело с `model`, `user` (id устройства),
`stream: false` и `messages`, ответ — обычный `chat.completion`. Каждый `user` получает
свою сессию: следующий запрос видит контекст предыдущего, а чат владельца в Telegram не
меняется. Сессия переживает перезапуск и обновление демона: история устройства, накопленная
прежней версией, переносится в сессию новой версии при его первом запросе. Задача выполняется ходом модели владельца с его инструментами;
`tool_choice: "none"` просит итог без новых действий: в таком ходе модель не получает ни
одного инструмента, даже подключённого раньше через `tool_search`. Бот всегда сам выбирает
flash, поэтому `model` в теле — только метка клиента: клиенты с `model: "dshbot"` и с любым
другим значением обслуживаются одинаково.

Запрос API ничего не пишет в Telegram: инструменты `message`, `plan`, `send_file`,
`skill_propose`, `ask_owner`, `self_change` и `self_submit` в его ходе отклоняются, фоновый
`delegate`, `task create` и немедленный запуск расписания (`schedule run_now`) не
запускаются: их итог уходит в чат владельца. Синхронный субагент наследует тот же запрет.
Действие, которому нужна карточка подтверждения владельца, отклоняется без карточки, а
предупреждение о канарейке остаётся в журнале демона. Создать, изменить
или посмотреть расписание на будущее и `set_next_wakeup` клиент может. Порт API
открывается после публикации меню команд при старте демона. Ход запроса
встаёт в общую очередь с ходами владельца и пробуждениями, как `/wake`: если владелец
сейчас переписывается с ботом, запрос ждёт конца его хода (клиенты обычно ждут ответа
до 180 с).

Порт и токен задаются в `~/.config/dshbot/dshbot.env`:

```sh
DSHBOT_OPENAI_PORT=8765
DSHBOT_OPENAI_TOKEN=<длинный случайный токен>
# Необязательно: адрес прослушивания, по умолчанию 127.0.0.1.
DSHBOT_OPENAI_HOST=127.0.0.1
```

Без `DSHBOT_OPENAI_PORT` или `DSHBOT_OPENAI_TOKEN` слушатель не открывается, и демон
работает как раньше. Порт, занятый другим процессом, тоже не останавливает демон: причина
пишется в журнал, Telegram продолжает работать.

Чтобы клиент закрепил сертификат в `tls_ca_file`, задайте оба файла PEM. Сертификат
должен быть выпущен на имя, которое клиент передаёт в `tls_server_name` (например,
`xiaozhi.test` или DNS-имя сервера); без пары `DSHBOT_OPENAI_TLS_CERT` и
`DSHBOT_OPENAI_TLS_KEY` эндпоинт работает по HTTP.

```sh
DSHBOT_OPENAI_TLS_CERT=/etc/dshbot/api-server.pem
DSHBOT_OPENAI_TLS_KEY=/etc/dshbot/api-server.key
```

Пример блока LLM в конфиге голосового клиента (у xiaozhi-server это `data/.config.yaml`
или профиль провайдера):

```yaml
LLM:
  provider: openai
  model: "dshbot"
  base_url: https://127.0.0.1:8765/v1
  api_key: <DSHBOT_OPENAI_TOKEN>
  tls_ca_file: /etc/dshbot/api-server.pem
  tls_server_name: xiaozhi.test
```

`base_url` обязан начинаться с `https://` и заканчиваться на `/v1` — клиент дописывает
`/chat/completions`. Токен и сертификат из блока должны совпадать с env-файлом демона.
После изменения env-файла перезапустите службу: `systemctl --user restart dshbot.service`.

### Очередь уведомлений сборщиков

Сборщики кладут карточки `<sha256>.json` в каталог `DSHBOT_NOTIFY_QUEUE` (по умолчанию `$DSHBOT_HOME/notification-queue`), а картинки — в `<родитель каталога>/artifacts/<id>.png`. Создайте каталоги и дайте сборщику право писать в них:

```sh
mkdir -p "$DSHBOT_HOME/notification-queue" "$DSHBOT_HOME/artifacts"
```

Демон сам опрашивает каталог раз в секунду и отправляет карточки владельцу в Telegram без хода модели. После успешной отправки файл получает суффикс `.accepted`, битый файл — `.rejected`; ошибка Telegram оставляет `.json` до следующего опроса. Карточки старше 24 часов при первом обнаружении приходят одной сводкой по источникам. До отправки демон сохраняет время первого обнаружения и SHA-256 карточки в `<имя>.json.seen` рядом с ней: сохраняйте эти служебные файлы вместе с ожидающими карточками при переносе очереди. Они переживают перезапуск и удаляются после принятия или отклонения карточки. Демону нужны права создавать и переименовывать файлы в каталоге очереди; ошибка чтения или записи отметки приостанавливает доставку с записью в журнал. Если `DSHBOT_NOTIFY_QUEUE` указывает на другой каталог, `artifacts/` лежит рядом с ним, а не в `DSHBOT_HOME`.

Ссылка `url` включается и в обычную карточку, и в подпись к изображению либо её продолжение, и в заголовок отчёта v3. Отчёт v3 сохраняет порядок текстовых блоков, фото, таблиц и разделителей; v2 показывается обычной карточкой. Текст экранируется для Telegram HTML. Лимиты 4096 единиц UTF-16 для сообщения и 1024 для подписи учитывают emoji; остаток длинной подписи и длинных ячеек уходит следующими сообщениями без потери текста. Все PNG карточки проверяются до отправки первого сообщения: нужны корректные чанки с CRC и непустые данные IDAT, одного IHDR и IEND недостаточно.

### Режимы изоляции

- `container` — весь демон запускается внутри `bwrap` с фейковым root: каталог приложения и тулчейн только для чтения, `DSHBOT_HOME` доступен на запись, сеть общая. Нужен `bwrap`; без него установка прекращается, а запуск без контейнера запрещён.
- `host` — демон запускается напрямую от вашего пользователя, без песочницы. Это режим по умолчанию (в том числе при пустом значении). Без `bwrap` установщик только предупреждает.

Подробнее о запуске — `scripts/dshbot-run.sh` и `docs/DESIGN.md`.

## Служба и автозапуск

Установщик выполняет `systemctl --user daemon-reload` и `systemctl --user enable --now dshbot.service`. Вторая служба, `dshbot-doctor.service`, запускается systemd через `OnFailure=` основной и отдельно не включается.

Пользовательские службы работают, пока есть активная сессия входа. Чтобы бот жил после выхода из системы, нужен lingering:

```sh
sudo loginctl enable-linger "$USER"
```

Установщик не вызывает `sudo`: если `Linger=no`, он печатает эту команду с объяснением.

Полезные команды:

```sh
systemctl --user status dshbot.service
systemctl --user restart dshbot.service
journalctl --user -u dshbot.service -f
```

## Привязка владельца

После первого сообщения боту в личку он печатает в журнал одноразовый код:

```text
pairing code for private chat <id>: <код>
```

Установщик ищет код только среди записей текущего запуска службы: после `start`/`restart` он берёт `InvocationID` (`systemctl --user show -p InvocationID --value dshbot.service`) и время запуска, а затем читает журнал с фильтром `_SYSTEMD_INVOCATION_ID` и `--since`. Поэтому код прошлой установки, оставшийся в журнале после `--purge` или повторного запуска, не будет напечатан вместо нового.

В интерактивном режиме установщик сам просит написать боту в личку и до 120 секунд ждёт появления кода текущего запуска, затем печатает код и объясняет, что отправить.

В режиме `--yes` установщик не ждёт: он печатает готовую команду с уже подставленными `InvocationID` и временем запуска, которой можно посмотреть код. То же вручную:

```sh
journalctl --user -u dshbot.service -n 200 --no-pager \
  "_SYSTEMD_INVOCATION_ID=$(systemctl --user show -p InvocationID --value dshbot.service)"
```

Код нужно отправить боту в личку одним сообщением — после этого чат становится владельцем.

## Обновление

Повторный запуск `scripts/install.sh` (интерактивно или с `--yes`) обновляет установку:

1. получает новую вершину из источника;
2. выполняет `npm ci` в каталоге приложения;
3. заново ставит юниты с актуальным путём к `node`;
4. перезапускает `dshbot.service`.

Если `~/.config/systemd/user/dshbot.service` или `dshbot-doctor.service` — симлинк прежней ручной установки на `deploy/*.service` в каталоге приложения, установщик заменяет сам симлинк обычным файлом. Шаблоны в `deploy/` не меняются, рабочее дерево приложения остаётся чистым.

Существующий `dshbot.env`, `state.db` и память не меняются.

Обновление бережёт данные:

- если в рабочем дереве приложения есть незакоммиченные изменения, установка останавливается с сообщением и ничего не меняет;
- если на ветви `live` есть локальные коммиты (правки самоэволюции), которых нет в новой версии, старая вершина помечается тегом `pre-install-<время>`, имя тега печатается;
- если каталог `app` существует, но это не установка DSHBOT (нет git-репозитория или ветви `live`), он не удаляется, а переносится рядом в каталог данных: `~/.local/share/dshbot/app.prev-<время>` (или `$DSHBOT_HOME/app.prev-<время>`); путь печатается.

Источник кода по умолчанию — корень репозитория, из которого запущен скрипт. Для другого checkout задайте `DSHBOT_INSTALL_SRC=/path/to/dshbot`.

## Удаление

Снять службы и удалить код, сохранив память и настройки:

```sh
scripts/install.sh --uninstall
```

Останавливаются и выключаются обе службы, удаляются файлы юнитов и каталог приложения. `DSHBOT_HOME` (память, `state.db`) и `~/.config/dshbot/dshbot.env` остаются.

Полное удаление, включая память и настройки:

```sh
scripts/install.sh --purge
```

Перед удалением установщик печатает точные пути и просит ввести слово `удалить`; любой другой ответ отменяет удаление, ничего не удалено. Флаг `--yes` заменяет это подтверждение: пути печатаются, и удаление выполняется сразу, без вопроса.

Путь `DSHBOT_HOME` сначала приводится к каноническому виду (симлинки и сегменты `.` и `..` раскрываются); проверяется, печатается и удаляется именно он. Если сам `DSHBOT_HOME` — симлинк, удаляется и он. Удаление отказывается работать даже с `--yes`, если путь пуст, не абсолютный, не существует, указывает на `/`, на домашний каталог или каталог над ним, либо в нём нет `state.db`. Неинтерактивный вариант:

```sh
DSHBOT_HOME=~/.local/share/dshbot scripts/install.sh --purge --yes
```

## Переменные окружения установщика

| Переменная | Значение |
| --- | --- |
| `TELEGRAM_BOT_TOKEN` | токен бота; без него интерактивный режим спросит, `--yes` завершится ошибкой |
| `DEEPSEEK_API_KEY` | ключ DeepSeek; то же правило |
| `DSHBOT_ISOLATION` | `container` или `host` (по умолчанию `host`) |
| `DSHBOT_HOME` | каталог данных вместо `~/.local/share/dshbot`; приложение ставится в `$DSHBOT_HOME/app`, путь прописывается в юниты. Нужен абсолютный путь без сегментов `.` и `..`, пробелов, кавычек и символов `\ % $`, не равный домашнему каталогу. Для обновления, `--uninstall` и `--purge` задавайте тот же `DSHBOT_HOME` |
| `DSHBOT_INSTALL_SRC` | каталог с исходниками вместо корня текущего репозитория |
| `DSHBOT_INSTALL_ORIGIN` | адрес `remote origin` приложения для `/update` и отправки правок в main вместо origin источника |

## Если что-то пошло не так

- `node ... ниже требуемой` — обновите Node.js до версии из `engines` в `package.json`.
- `не найден git` — установите git.
- `режим container требует bwrap` — установите bubblewrap или используйте `DSHBOT_ISOLATION=host`.
- Служба не стартует — `journalctl --user -u dshbot.service -n 100 --no-pager`; отдельный доктор `dshbot-doctor.service` пишет владельцу в Telegram, когда основная служба упала.
- Код привязки не появился — убедитесь, что бот получил сообщение в личку, и посмотрите журнал текущего запуска: `journalctl --user -u dshbot.service -f "_SYSTEMD_INVOCATION_ID=$(systemctl --user show -p InvocationID --value dshbot.service)"`. Если в выводе виден код прошлой установки, проверьте `InvocationID`: после перезапуска службы он меняется, а старые записи журнала остаются.
